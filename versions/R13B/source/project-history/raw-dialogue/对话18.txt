## 2. §2B：fallback 重复上报已定位到源码并修正

**现象（旧候选 `d2100afa` 的原始日志，无任何 reader 端 dedupe）**

| 局 | fallback 事件 | distinct 决策 | per-key 直方图 |
| --- | --- | --- | --- |
| 冰岛 `4d07a05b` | **16** | 8 | 8 个 key 全部 `emitted=2` |
| 巨岛 `26d18c53` | **45** | 36 | 9 个 key `emitted=2`，27 个 `emitted=1` |

**根因（不是 cadence、不是工具）**：工厂循环里有**两个 block 会到达同一决策并各自写事件**：

1. 《输出15》机会性投资 block（第 342/356 行）；
2. army-cap banking block（`army>=10 && chosenUpgrade!=null`，原第 382 行）→ 又调了一次 `reportSecondaryFallback`。

所以一次决策写出两条 fallback，`production_deferred` 因为自带 10 游戏秒窗口只写一条 —— 这正是日志里 `DEFER ×1 + FALLBACK ×2` 的形态。

**修正**：新增唯一 owner，两个 block 都只调用它：

```java
// upgrade==null → 直接返回（同时覆盖 §1 的 phantom 抑制）
// 同厂同因 10 游戏秒窗口内 → 返回
// 否则写 (SECONDARY_INVESTMENT_DEFERRED, SECONDARY_INVESTMENT_FALLBACK) 一对
private void reportSecondaryInvestment(factory, upgrade, unit, state, bankedReserve, primaryReserve)
private boolean mayReportSecondaryInvestment(factory)
```

两个 block 各自的 `reportProductionDeferred` / `reportSecondaryFallback` 直接调用已删除；**下单路径一行未改**（`post("/command/queue")` 仍在原处、原条件）。phatom 抑制也随之收敛到 owner 内部（`upgrade==null` 直接返回），比 4 行 `if` 更彻底。

**离线复现**（`_analysis\fallback_rehearsal.py`，用与套件相同的 fixture，让该厂每个 tick 重复同一决策、队列始终为空）：

```text
生产决策 tick = 3        secondary 下单 = 3
fallback 事件 = 1        distinct key = 1        per-key = {1: 1}
次要 deferral 事件 = 1   （与 fallback 1:1 配对）
RESULT: PASS
```

修正前同一 fixture 是 `fallback = 6 / distinct = 3，per-key {2: 3}`，即每次决策两条。**这是源头修正，分析工具不再依赖事后 dedupe**（`p2b2_metrics.py` 里那个 distinct 统计只是展示层，保留但不再必需）。

**新增 regression test**：`test_one_fallback_decision_writes_exactly_one_event` —— 断言 fallback 事件数 == distinct key 数、且与配对 deferral 数相等、且仍然下单（报告修正不得改变生产）。
