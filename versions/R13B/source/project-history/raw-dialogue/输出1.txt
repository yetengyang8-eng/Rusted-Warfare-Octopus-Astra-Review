# 1. 下一步顺序

我的建议不是“先完整验收”或“完全不验收”，而是分成两个层次：

### 第一步：干净环境冒烟验证

你现在已经有一个去除了 RWPP 残留、hash 与基线一致的原版 1.15 副本。

先把当前冻结版 0.07 装进去，只验证：

1. Agent 能正确加载；
2. VERSION/hash/路径日志正确；
3. 能进入一局；
4. 能产生正常 economy/development/battle 日志；
5. 游戏退出后报告能正常封存。

不需要为了这一轮冒烟测试硬跑完整 900 秒。

### 第二步：修复收尾死锁

然后再修改搜索/目标回落逻辑。

### 第三步：正式 Windows 实机验收

修完以后马上跑完整实机局，验证：

* 是否仍出现 `NO_REACHABLE_UNVISITED_FRONTIER` 无限循环；
* 是否能重新发现敌人；
* 是否能够正常走到 VICTORY / DEFEAT / TIMEOUT；
* 报告是否完整封存。

所以顺序是：

**环境可信 → 修行为 → 完整验收**

而不是拿当前已知存在搜索停摆风险的版本反复跑长局。

# 2. 九图地图池到底是什么

项目长期讨论中已经固定过九图名单：

* 冰岛
* 登岛
* 巨岛
* 直岛
* 小岛
* 两极
* 火桥
* 山丘
* 湖陆

因此 `ROADMAP_CN.md` 所说的“九张地图”，历史上指的就是这一组。

但我要强调：

**九图池 ≠ 当前 0.07 必须已经能够在九图全部获胜。**

0.07 当前明确还没有空军/海军/运输等完整跨地形体系，因此不能仅凭地图属于九图池，就把“敌人在另一不可达连通区域”认定为陆军搜索算法 bug。

建议你不要根据地图名字猜，而是让地图解析器明确回答：

> 对当前陆军 movement type 而言，敌我出生区域是否属于同一可达连通分量？

然后把失败分成两类：

### A. 同一陆军连通区域，但只探索 51% 就报无前沿

这是规划器 bug。

### B. 剩余未探索区域属于陆军不可达连通分量

这是当前能力边界。

这样以后日志里甚至可以直接输出：

`reachableMapRatio`

例如：

`landReachableTiles / totalLandTiles`

而不是只输出全地图 explored ratio。

这样可以避免把“海的另一边没探索”误判成搜索失败。

# 3. 关于敌人记忆：你的方向是对的

我赞成你提出的：

> 移动敌人的精确战术记忆过期后，不再使用其位置/血量作为实时信息，但保留“最后目击地点”作为搜索目标。

建议明确拆成两层。

## 第一层：战术记忆

例如当前 20 游戏秒。

有效期内可以认为：

“敌人大概率仍在这个区域。”

可以用于：

* attackMove；
* 追击；
* 局部战斗决策。

时间到以后失效。

## 第二层：搜索记忆

保存：

`lastSeenPosition`

但其语义不是：

> 敌人现在就在这里。

而是：

> 我最后一次确认敌人在这里，因此这里值得重新侦察。

这个坐标可以长期存在，直到：

1. 该位置重新进入合法视野；
2. 在一定搜索半径内确认没有该目标；
3. 或新的敌情产生更高优先级搜索目标。

这样不违反战争迷雾规则。

关键底线是：

**过期以后不能继续获得任何来自迷雾中的位置、血量、移动方向更新。**

“记住自己曾经看到过什么”是合法历史信息；
“敌人进入迷雾后继续追踪它现在在哪里”才是作弊。

# 4. 搜索死锁不建议只用“最后目击点”修

最后目击点应该加，但它只是第一层 fallback。

我建议把目标选择做成明确的降级链：

### Priority 1

当前合法视野中的敌人

↓

### Priority 2

仍处于战术记忆有效期的敌人

↓

### Priority 3

最后目击地点 / 高价值敌方建筑历史位置

↓

### Priority 4

当前部队可达的未探索 frontier

↓

### Priority 5

更换搜索锚点重新求 frontier

↓

### Priority 6

根据己方所有机动单位可达区域求 frontier，而不是只依赖单个 unit anchor

↓

### Priority 7

如果当前陆军可达区域已经完全探索，则明确产生：

`LAND_SEARCH_EXHAUSTED`

而不是无限重复：

`NO_REACHABLE_UNVISITED_FRONTIER`

这样 Agent 至少能够知道：

> “我搜索完了我现在能走到的地方。”

这个状态以后才能触发：

* 造空军；
* 造海军；
* 运输；
* 或报告当前能力无法完成地图。

你怀疑现在 frontier 被 `builderId:153` 这样的单个锚点绑死，我认为非常值得检查。

如果全图探索只有 51%，而单 anchor reachableTiles=3255 后直接宣布没有 frontier，这个结构本身就很可疑。

# 5. 20 秒记忆是否过短

目前先不要单独把 20 秒改成 40/60 秒。

因为真正的问题不是“20 秒还是 30 秒”，而是：

> 战术记忆一过期，系统直接从“知道敌人大概在哪”跳成“完全不知道该干什么”。

先建立上面的两层记忆和 fallback 链。

之后再通过实战数据调整 tactical memory duration。

否则直接延长到 60 秒只是把死锁从 335 秒推迟到 375 秒，并没有解决结构问题。

# 6. 持续经济应当升级，但排在搜索闭环之后

我支持你把持续经济提升为下一阶段核心能力。

项目之前 0.07 的突破，本质是：

> 能从标准开局自主走到战争并取得原生 VICTORY。

下一阶段要从“偶尔完整打一局”向稳定自治推进，经济必须从一次性 opening script 变成持续系统。

优先内容建议是：

1. 建造者死亡后的补充；
2. 关键经济建筑损失后的重建；
3. 第二矿/后续矿点扩张；
4. 持续补兵；
5. 工厂损失后的重建；
6. 维修；
7. 根据经济规模扩充生产能力。

不过这里有一个需要先厘清的问题：

当前 `armyCap=24` 到底是：

* Agent 自己人为设定的目标军队规模；
  还是
* 游戏真正的单位上限？

如果只是 Agent 策略上限，那么“24 满编 → queue=0 → 11206 钱不花”本身就是策略设计问题。

后续应允许：

* 扩大战斗编队；
* 建立预备队；
* 或把资源转化为经济/生产/科技。

如果 24 是为了当前测试人为限制的安全阈值，则不要为了花钱盲目造第二、第三工厂。

# 8. 关于这局我还想提醒一个地方

日志 701.5 游戏秒停止，但游戏又运行了约 71 秒才由菜单退出。

因此后续干净实机验收时，请顺便观察：

> 为什么 battle report 在游戏真正退出前约 71 秒停止产生事件？

如果只是这 71 秒没有任何值得记录的事件，那没问题。

如果实际上连 heartbeat / observation / decision tick 都停止，那么这里还可能存在：

**Agent 主循环或记录器停止工作**

而不仅仅是 army planner 没有目标。

建议至少加一个低频 heartbeat，例如每 10 游戏秒：

`agent_tick_alive`

其中带：

* gameSeconds
* currentPhase
* currentGoal
* visibleEnemies
* tacticalMemories
* searchTargets
* exploredTiles
* reachableUnvisitedTiles

这样以后看到“军队不动”，可以立即区分：

1. Agent 正常运行但策略决定 WAIT；
2. planner 没目标；
3. 主循环已经死掉。

## 最终建议

目前不要扩大战术复杂度。

先把 Agent 建成一个**不会无声停机的闭环系统**：

> 看见敌人 → 战斗 → 丢失敌人 → 去最后目击点 → 搜索可达区域 → 换锚点继续搜索 → 再接敌 → 战斗 → 直到游戏原生结算。

如果可达区域全部搜索完仍找不到敌人，则明确输出：

> 当前 movement capability 无法继续搜索。

而不是无限原地等待。

做到这一层以后，0.07 的“能够完成一局”才会开始从**成功案例**变成**系统能力**。

之后再把持续经济补上，我认为就是目前从 0.1 原型向 0.3 稳定自治推进最顺的路线。
