## 1. 半成品恢复的真实闭环（测试逐帧验证）

`RecoveryProbeTests` 用一条完整时间线跑通，事件顺序与《输出10》§11 要求一致：

```text
economy_expansion_planned                计划矿点 (1500,1000)
economy_expansion_started / _observed    工地出现，buildProgress=0.4
own_loss(builder)                        唯一建造者死亡
economy_expansion_state: STALLED_NO_BUILDER   ← 保留 unitId=77 / site / buildProgress=0.4
builder_recovery_started → _ordered      新建造者下单（原生 500）
builder_recovery_completed
economy_expansion_recovery_probe         RECOVERY_PROBE（同一 site，只此一次）
economy_expansion_recovery_probe_accepted RECOVERY_PROBE_ACCEPTED（≠ 恢复）
economy_expansion_recovery_resumed       ACTIVE，buildProgress 0.4 → 0.8（resumedFrom=0.4）
```

关键否定性断言（防止「假 ACTIVE」）：

- `_state` 序列里**只有** `STALLED_NO_BUILDER`，没有提前写 `ACTIVE`；
- `recovery_resumed` 的时间戳晚于 `probe_accepted`，且 `buildProgress` 严格上涨；
- 全流程只发出 **2 条** `build-extractor`（原始 1 条 + 探针 1 条），没有重试循环。

拒绝分支（`probe_accepted=False`）：`recovery_probe_rejected` 恰好 1 条 → 只读动作清单（`hasResumeAction=false`）→ `ABANDONED_UNRECOVERABLE`（`blockedSite=1500,1000`）→ 之后 planner 命中同一点时报 `economy_expansion_blocked: UNUSABLE_UNFINISHED_SITE`，**永不出现 recovery_resumed**，也不会 probe→abandon→replan 死循环。

顺带修掉一个我自己引入的缺陷：探针原本在「正常施工中 + 刚好有 builder」时也会触发（会在工地刚出现时多发一条 build 命令）。现在只有真正经历过 `STALLED` 的 job 才会探测（新增 `wasStalled` 门控）。

## 2. 关于《输出10》§6/§7：原版没有 repair/assist 续建路径

新增的只读端点 `GET /economy/builder-actions?unitId=` 在原生夹具里给出建造者的完整动作清单（**13 个动作**）：

```text
class m type=upgrade  id=ActionId(c_2)              cost=0      ← 非建造动作
class v type=extractor          id=b_extractor          cost=700
class v type=turret             id=b_turret             cost=500
class v type=antiAirTurret      id=b_antiAirTurret      cost=600
class v type=landFactory        id=b_landFactory        cost=700
class v type=airFactory         id=b_airFactory         cost=1000
class v type=seaFactory         id=b_seaFactory         cost=1000
class v type=laserDefence       id=b_laserDefence       cost=1200
class v type=repairbay          id=b_repairbay          cost=1500
class v type=fabricator         id=b_fabricator         cost=1500
class v type=experimentalLandFactory / NukeLaucher / AntiNukeLaucher
```

**没有任何 repair / assist / reclaim / continue 类动作**：建造者对建筑只有「同名 build」。所以续建半成品在原版里唯一的候选路径就是「对同一 site 重新下达同名 build」，这已经在第 1 节验证——原生接受该命令，并且（在测试引擎里）原结构进度确实继续上涨。

注意：`hasResumeAction` 字段目前把 build 动作也算作「可能的续建路径」（`resumeAction=true`），因为它正是我们唯一可用的手段；`repair/assist/reclaim/continue` 命中时为真但当前不存在。实机上若探针被 409 拒绝，这一字段会是判断「还能不能救」的直接证据。

## 3. 只读 capability 端点（《输出10》§13 的实机采集通道）

`GET /combat/capabilities?types=c_tank,heavyTank,hoverTank`（可省略 `types`，则取当前我方 + **当前可见**敌方的全部类型，上限 16）：

```json
{"status":"observed","units":[{"type":"builder","side":"own","price":500,
  "booleans":{"y.ax":true,"am.cK":true,"y.h":false,...}}],"unavailable":["unknownUnit"]}
```

- 字段名是混淆名（`y.ax`、`am.cK`…），所以它的用途是**实机差分**：c_tank 的真值已知（`canAttackFlyingUnits=false`、`canAttackLandUnits=true`，来自 `assets/units/tanks/tank.ini`），把 c_tank / heavyTank / hoverTank 三者的布尔集合并排，就能锁定「对空/对地」两个标志位并读出 heavyTank。若困难 AI 局里出现 `c_antiAirTurret`（ini 已知 air=true / land=false）就是完美的正向对照。
- 敌方类型严格沿用现有的双重可见性判定（`u.d(bs)` + `bL.a(x,y,bs)`），不读隐藏敌人；每类只取一个代表实例，最多 16 类、每类最多 80 个布尔字段。
