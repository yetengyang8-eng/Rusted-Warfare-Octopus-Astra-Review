## 2. 客户端恢复闭环（`BattleClient.builderRecovery`）

```text
aliveBuilders == 0 且无在产        -> builder_recovery_started
GET /economy/builder-production    -> builderCost 记入 builderReserve（优先级高于一切战斗生产）
生产者队列非空                     -> builder_recovery_waiting: PRODUCER_BUSY
credits < builderCost              -> builder_recovery_waiting: INSUFFICIENT_CREDITS
动作不可用 / 无生产者              -> builder_recovery_waiting: ACTION_UNAVAILABLE
队列空闲且钱够                     -> POST -> builder_recovery_ordered（builderOrderPending=true）
新建造者出现                       -> builder_recovery_completed（释放 reserve）
```

- 预留语义：`wouldBreachMineReserve` 现在同时计入 **builderReserve** 与在建工地预留；因此「builder 已死但工厂还在花钱」不会再把钱花光——这正是《输出9》§4 要防的情形。
- 诊断区分：被预留挡下的购买写 `production_deferred {reason: RESERVED_FOR_BUILDER_RECOVERY, reservedFor: BUILDER_RECOVERY, reservedCost: 500, candidateUnit, candidateCost, credits, factoryTier}`；「钱不够只能买便宜货」仍是 `production_decision: PREFERRED_UNAFFORDABLE_FALLBACK`。两者语义不再混淆。
- 心跳新增 `aliveBuilders / builderRecovery / builderOrderPending / builderReserve / builderCost / builderProducerId`；汇总新增 `builderTarget / builderRecoveries / builderOrders`。
- `BuilderRecoveryTests` 用一条时间线覆盖：CC 忙 → 等待；钱不足 → 等待；钱到位 → 下单；建造者出现 → 完成；并断言**在下单之前没有任何战斗单位被购买**（预留真的挡住了）。
