# 1. P1 内部顺序：先做“最后目击点”，但不能单独交付

我同意你在编码顺序上：

1. 最后目击点搜索目标；
2. frontier  reachable anchor 修复；
3. 完整 fallback 链；
4. 状态日志；
5. 再跑实机。

原因是最后目击点机制简单、语义明确，而且这局有一个非常漂亮的测试样本：

`builder @ (653.7,1595.1)`

你很容易验证：

 战术记忆过期以后，Agent 是否仍然会主动前往这个历史位置。

所以它适合作为第一块实现。

但是这里要区分：

### 开发顺序

可以：

lastSeen → frontier

### 验收顺序

不可以：

lastSeen 做完 → 马上宣布 P1 修好

因为真实情况可能变成：

```text
敌人消失
↓
前往最后目击点
↓
看到那里没人
↓
lastSeen 被正确清除
↓
再次调用 frontier
↓
NO_REACHABLE_UNVISITED_FRONTIER
↓
重新停机
```

也就是说，lastSeen 只能把死锁向后推几十秒。

因此我建议把 P1 定义成一个完整状态链：

```text
VISIBLE_ENEMY
    ↓
TACTICAL_MEMORY
    ↓
LAST_SEEN_SEARCH
    ↓
FRONTIER_SEARCH
    ↓
REANCHOR  GLOBAL_REACHABLE_SEARCH
    ↓
LAND_SEARCH_EXHAUSTED
```

只有整条链打通，P1 才算完成。

# 2. 关于“锚点 bug”：目前高度可疑，但不要把 32% 当作已经证明的根因

这里我想稍微收紧一下措辞。

当前证据说明：

 冰岛最大陆地连通分量约 10112 格；
 planner 某次只报告 reachableTiles=3255；
 frontier 长期返回 `NO_REACHABLE_UNVISITED_FRONTIER`；
 地图仍明显存在大量未搜索区域。

这足以证明：

 当前搜索规划器对“哪里还能搜索”的判断存在严重问题。

但暂时还不能严格证明：

 “唯一根因就是使用了单个 heavyTank 作为 anchor。”

因为还有几个可能性：

 reachableTiles 的定义并不是“该单位全局可达格”；
 planner 对 frontier 又进行了其他过滤；
 clearance  建筑  path group 与你离线的 8 连通不同；
 explored 集合和 reachable 集合的坐标体系或语义不同。

另外：

`exploredTiles=10717`

不能直接和：

`landTiles=10112`

比较后推出“整块陆地已经探索完”。

因为 explored 很可能同时包含：

 水面；
 不可通行地形；
 视野扫过但不能站立的 tile。

所以这个数字支持“地图看过很多”，但不能作为陆地覆盖率。

因此建议代码里直接把中间量打出来。

# 4. 不建议每 tick 都真的对“所有单位可达域”做昂贵并集

你之前引用我的 Priority 6：

 根据所有机动单位可达区域求 frontier。

这个逻辑方向没问题，但实现时不要机械地真的让 24～32 辆坦克每秒各做一次 flood fill。

更好的优先顺序是：

### 第一层

当前 anchor 求 frontier。

如果成功，直接使用。

### 第二层

anchor 无 frontier：

尝试选择不同空间位置的单位重新 anchor。

例如：

 离当前 anchor 最远的单位；
 离 unexplored 区域最近的单位；
 当前先锋单位；
 最近完成移动的单位。

### 第三层

多个代表 anchor 都失败后，再做 global reachable  union fallback。

这样正常情况下成本很低，只有异常状态才触发昂贵搜索。

# 5. `armyCap=24`：目前没有可靠历史证据表明它是竞技规则

我这里没有项目历史证据可以证明：

 24 是为了模拟真人 APM 而刻意设计的长期限制。

相反，从项目结构来看，我更倾向把它理解成：

 早期 Agent 为了控制复杂度设置的策略安全阈值。

而且我认为：

限制 APM 和限制单位数量，本质上是两件事。

真人即使拥有 50 个单位，也不意味着需要同时对 50 个单位分别下指令。

完全可以：

```text
50 units
↓
选中整个编队
↓
1 个 attackMove
```

只产生一次 command。

所以未来真正应该限制的是：

 commandsmin；
 minimum command gap；
 reaction latency；
 information access；

而不是用：

`army.size()  24`

替代真人操作约束。

# 6. 但我不建议 P1 直接取消 24 上限

不要这轮突然从：

`24`

改成：

`∞`

因为这样会同时改变：

 经济；
 兵力规模；
 战斗结果；
 寻路压力；
 CPU；
 APM；
 验收基线。

那就很难判断 P1 的成功到底来自搜索修复还是单纯兵更多了。

我的建议是把一个变量拆成三个概念。

例如：

```text
activeArmyTarget = 24
reserveTarget = 8
mobileUnitHardCap = 32
```

第一版数字不需要被当作永久设计，只作为可配置初值。

语义：

### activeArmyTarget

主战编队期望规模。

目前继续保持 24，最大程度兼容 0.07 行为。

### reserveTarget

额外生产少量预备兵。

例如 8。

这些单位：

 不需要频繁单独操作；
 可以留在基地；
 主战单位阵亡以后补入；
 或形成下一波。

### mobileUnitHardCap

真正的安全上限。

例如先设成：

`32`

这样：

```text
24 主力 + 8 预备
```

既修复：

 满 24 后 produce() 永久 silent

又不会突然让 Agent 无限暴兵。

# 10. 避免 lastSeen ping-pong 的具体规则

我建议第一版规则尽量简单而严格。

## 创建

只有新的合法敌方 observation可以创建或刷新 search target。

不能因为：

 remembered enemy；
 上一轮 stale target；
 推测；

不断重新生成。

---

## 激活

当不存在：

 visible enemy；
 tactical memory；

才允许选择 lastSeen search target。

---

## 到达

不要用：

 单位坐标距离目标  X

作为唯一完成条件。

应该要求：

 lastSeen 所在 tile 已重新进入己方合法视野。

这是最重要的判据。

因为真正要确认的是：

 “我重新检查过这里。”

而不是：

 “有辆坦克走近过这里。”

---

## 清除

如果 lastSeen tile 重新进入合法视野，而目标敌人不存在：

```text
CONFIRMED_EMPTY
```

立即消费掉这个 search target。

以后不能根据那条旧 observation 再创建一次。

---

# 11. 给已消费目标留下 tombstone

这是防止 ping-pong 最简单的方法。

例如：

```text
enemyId=7
lastSeenAt=314.8
position=(653.7,1595.1)

search result
CONFIRMED_EMPTY
```

保存一个 tombstone：

```text
consumedObservationTime=314.8
```

只有当：

```text
enemyId=7
```

之后产生：

```text
newObservationTime  314.8
```

才能再次生成目标。

这样旧情报永远不会复活。

---

# 12. 其他终止状态

建议 SearchTarget 至少有：

```text
ACTIVE
CONFIRMED_EMPTY
SUPERSEDED
UNREACHABLE
```

### CONFIRMED_EMPTY

目标区域重新获得视野，没有找到对应目标。

### SUPERSEDED

出现更新的敌情。

例如 enemyId=7：

旧：

```text
(653,1595) @ 314s
```

后来重新看到：

```text
(820,1470) @ 390s
```

旧目标立即废弃。

### UNREACHABLE

native pathfinding 明确无法到达。

然后进入 frontier fallback。

不要每秒重新请求同一个 unreachable target。

# 13. 避免两个历史目标之间来回跳

假设：

```text
Target A
Target B
```

不要：

```text
A
↓
走一半
↓
B 稍微评分高一点
↓
掉头
↓
A 又变高
```

第一版直接采用目标黏性：

一旦进入：

`LAST_SEEN_SEARCH`

只允许以下事件抢占：

1. 当前视野出现敌人；
2. 新 tactical memory；
3. 当前 target 被判定 unreachable；
4. target 被确认 empty。

其他历史 lastSeen 不抢占。

这比每秒动态评分稳定得多。

## 最后裁决

四个问题对应我的答案：

### 1. 先 lastSeen 还是 anchor？

编码先 lastSeen；交付必须同时修 anchorfrontier。

lastSeen 是快速有效的第一层 fallback，但不能成为掩盖根因的补丁。

### 2. armyCap=24 怎么处理？

没有可靠证据证明 24 是长期竞技规则。

先视作早期安全阈值。

不要取消，而是拆成：

```text
24 active + 8 reserve + 32 hard cap
```

并全部配置化。

第二工厂留 P2。

### 3. lastSeen 怎样终止避免 ping-pong？

核心规则：

 目标 tile 被重新合法观察后，如果目标不存在，则该 observation 永久消费。

使用 tombstone 防止旧 observation 复活。

只允许新 observation 创建新的 search target。

执行中使用目标黏性，不允许 stale target 互相抢占。

### 4. A 类还需要什么证据？

当前证据足够进入 P1。

不需要先做九图表。

最有价值的下一份证据是：

 运行时 native pathfinder 对“当前坦克 → 最后目击点”的可达性判断。

之后再用 runtime reachableMapRatio 校验。

九图离线连通基线放 P1 之后。

你现在可以开始修改代码。
