## 1. 续建的经济语义：已记录、已判定、已双向测试

探针与恢复事件现在带齐《输出11》§2 要求的字段：

```text
*_recovery_probe            creditsBeforeProbe, buildCost, buildProgress, candidateId, site
*_recovery_probe_accepted   同上（= 命令被接受，仍不等于恢复）
*_recovery_probe_rejected   上述字段 + reason
*_recovery_resumed          buildProgressBefore / buildProgressAfter / creditsBeforeProbe /
                            creditsAfterProbe / probeCostDelta / buildCost
```

判定规则（写进代码，不只写在文档里）：

```text
chargedAgain = (creditsBeforeProbe - creditsAfterProbe) >= 0.9 * buildCost
progress>probeProgress && !secondStructure && !chargedAgain  -> RECOVERY resumed (ACTIVE)
progress>probeProgress &&  chargedAgain                      -> REJECTED: DOUBLE_CHARGED_BUILD_COST
                                                                -> ABANDONED_UNRECOVERABLE -> blockedSite -> replan
```

两条时间线都成了回归用例（`RecoveryProbeTests`）：

- **干净续建**：`creditsBeforeProbe=3000 → creditsAfterProbe=3000`、`probeCostDelta=0`、`buildProgress 0.4 → 0.8` → `recovery_resumed`；
- **重复收费**：`creditsAfterProbe=2300`、`probeCostDelta=700`（= 矿价 700）、`buildProgress 0.4 → 0.8` → **绝不写 resumed**，而是 `recovery_probe_rejected: DOUBLE_CHARGED_BUILD_COST` → `abandoned_unrecoverable(blockedSite=1500,1000)`。

也就是说：**即使进度真的涨了，只要又扣了一次完整建造费，就不算有效恢复**，直接走《输出11》§3 允许的「干净失败」路径。

需要你在实机证据上确认的一点（我无法在夹具里代表原版真实行为）：夹具证明了判定逻辑正确，但**原版对半成品重新下达同名 build 时到底收不收费**，要看下一局的 `probeCostDelta`。若实机出现 `probeCostDelta >= 0.9*buildCost`，说明原版确实重复收费，那 P2-C1-B 的终态就会是 `ABANDONED_UNRECOVERABLE + replan` 而不是 `resumed`——按你的裁决，这仍然算 P2-C1 通过（§14/§16 的两种合法终态之一）。

## 2. blockedSites 的最小语义（§5/§6）

```text
ABANDONED_UNRECOVERABLE -> blockedSites.put(site -> candidateId)
每个 tick prune：该 candidate 不存在 / 已死亡 / buildProgress>=1  -> 解除封锁
```

- 只在本局内存里，不跨局持久化（符合 §5）；
- 只要该 tile 上不再有**未完工**结构就解除（符合 §6）；
- 封锁期间 planner 若再次选中同一 tile，写 `economy_expansion_blocked: UNUSABLE_UNFINISHED_SITE` / `production_facility_blocked`，不产生 probe→abandon→replan 死循环。

## 4. 施工细节与偏差说明

1. **字段改名是破坏性的**（旧 `hasResumeAction` 已移除）。当前只有本项目内部的 harness / 测试读取它，均已同步改为 `hasRecoveryPath` + `recoveryPath`，并在 `BuilderHarness` 里断言 `recoveryPath == SAME_BUILD_COMMAND`。
2. 一个我自己引入的缺陷已修：探针原先在「正常施工中且恰好有 builder」时也会触发（工地刚出现就多发一条 build 命令）。现在只有真正经历过 `STALLED` 的 job 才会探测（`wasStalled` 门控）。
3. 一次工具事故记录：我用 PowerShell 的 `Set-Content -Encoding UTF8` 改测试文件时，把其中的中文注释按本地代码页往返编码弄坏了一次；已按编码反变换精确修复（该文件只有注释受影响，代码与断言无损），并改用编辑工具做后续改动。
