## 1. `production_decision` 的实际字段与触发

只在「该厂当前空闲、且真的下了单、且选中的单位与 preferred 不同」时写一条：

```json
{"factoryId":5,"factoryTier":2,"credits":500.0,"preferredUnit":"heavyTank","preferredUnitCost":800,
 "preferredAffordable":false,"bestAffordableUnit":"c_tank","bestAffordableCost":350,
 "chosenUnit":"c_tank","reason":"PREFERRED_UNAFFORDABLE_FALLBACK","gameTimeMs":...}
```

- `PREFERRED_UNAFFORDABLE_FALLBACK`：偏好买不起、退化为可负担项（即《输出8》要抓的资金争抢链）；
- `PREFERRED_SUPERSEDED`：偏好买得起但被更高评分项取代（例如 upgrade，score 5 > heavyTank 3）；
- 未来 P2-B2 引入预算保留后，可在此加 `RESERVED_FOR_PRIMARY_PRODUCTION`。

两条新测试锁住语义：`credits=500` → 必须出现 `PREFERRED_UNAFFORDABLE_FALLBACK`（preferred=heavyTank/800、chosen=c_tank/350）；`credits=2000` → 不得出现 fallback，且真的下单了 `heavyTank`。

## 3. P2-C1 的可行性与我的实现计划（等确认后施工）

按《输出8》§2 选 (a) 专用端点，最小化：

```text
GET  /economy/builder-production
     -> { status, producerId, producerType, queueCount, builderActionId, builderActionAvailable,
          builderCost, availableCredits, existingBuilders, builderOrderPending }
POST /command/produce-builder?unitId=<producerId>&actionId=<...>&sessionId=&requestId=
     -> 与既有命令相同的 receipt/去重/会话校验；ownership + allowlist + 队列为空 + 已有/已排建造者则拒绝
```

内部抽一个 producer helper（`buildAction` 同款），外部 API 保持专用；不改 `/combat/production` 语义。

客户端侧（`BattleClient`）的最小闭环：

```text
builderTarget = 1
1. 心跳/状态里统计 alive builder 数
2. == 0 且没有在产建造者 -> 取 /economy/builder-production，若 available 且 affordable 且队列空 -> 下单
3. 下单后用现有的 pending/观察机制确认新 builder 出现
4. 工地续建（《输出8》§3 验收项）：
   - 若原生能对半成品续建 -> STALLED_NO_BUILDER -> 派新 builder 去续建
   - 若原生/桥接不能续建 -> STALLED_NO_BUILDER -> ABANDONED_UNRECOVERABLE，随后重新规划
   - 绝不允许「状态回到 ACTIVE 但永远没有单位施工」
```

`STALLED` 状态与工地信息（`candidateId/site/buildProgress`）我上一轮已经实现并保留，P2-C1 直接复用；续建可行性的核查（第 2 节 §3 那条）会作为 P2-C1 的第一个验收项，若原生不支持则会显式走 `ABANDONED_UNRECOVERABLE`，不会留下假 ACTIVE。
