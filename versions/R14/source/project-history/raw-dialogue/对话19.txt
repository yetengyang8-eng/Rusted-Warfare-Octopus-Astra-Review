### 1.1 「32→40 是否真实提高经济向战斗力转换？」——**是，而且幅度很大**

1. **兵力维持时间**：`army≥32` 的心跳占比 22.7% → **61.4%**，跨度 37.9% → 63.1%。基线是"够到 32 又被压回去"，实验是"从 330s 起基本常驻 32+"。
2. **资金→战斗力的转换**：cap 期间 credits 中位 **2423 → 5307**。注意这不是"钱更多了所以更能攒"，而是**同样的收入水平下、账上滞留的钱多了一倍**——而同期 `lost` 从 64 降到 **29**。基线是"钱堆着、兵被打光、再买、再被打光"的循环（produced 73 / lost 64，几乎全损）；实验是 produced 63 / lost 29，**净存续 34 vs 9**。
3. **结论**：32 确实是经济转换的硬约束，不是"AI 本来就没钱"。

### 1.2 「40 是否又成为新的明显长期瓶颈？」——**是，但没有 32 那么致命**

- `army≥40` 占 **33.0% 心跳、56.2% 跨度**，`MOBILE_UNIT_HARD_CAP_REACHED` 占 **31.8% 心跳**（基线 22.7%）。
- 但这两者的性质不同：基线 cap=32 时 credits 中位 2423、峰值 6944 **无法转换**，且同期损失惨重（lost 64）；实验 cap=40 时 credits 中位 5210、峰值 10754 同样滞留，但同期 **lost 仅 29**，说明多出来的 8 个兵位确实换成了战场存续力。
- 若继续升 48，预期是同一模式的延伸（滞留资金更多），因此**不建议**直接继续加码；按《输出18》§7 的指示，这一局的肉眼观察（见 §4）才是决定下一步是 `LOW_VALUE_TARGET_PURSUIT_LIMIT` 还是继续加 cap 的关键。

## 3. §D：fallback 报告语义已按新定义修正（behaviour 事件）

**问题确认**：上一版把 fallback 也放进了 10 游戏秒节流窗口，导致 `3 次成功下单 / 1 条事件`（漏报）。你的判断正确。

**新语义（已实现）**：

```text
SECONDARY_INVESTMENT_DEFERRED  = 状态事件，保留 10 游戏秒节流
SECONDARY_INVESTMENT_FALLBACK  = 行为事件：
    decide fallback → POST /command/queue → 桥接接受 → 才写 1 条
    桥接拒绝（409/失败）→ 0 条
```

实现：`reportSecondaryInvestment(...)` 只负责写节流后的 deferral 并**登记** `pendingFallback`；生产者在下单 POST **成功之后**才写 fallback 事件（`post(...)==null` 直接 return，因此失败不写）。每个工厂迭代开始时清空 `pendingFallback`，防止跨厂串味。**下单路径一行未改。**

**新增/更新测试（`ProductionBudgetTests`，全套 37 OK）**：

| 测试 | 断言 | 结果 |
| --- | --- | --- |
| `test_three_quick_fallback_orders_write_three_events` | 3 个 tick（4s/6s/8s，间隔 < 10s）内 3 次成功下单 → **3 queue success / 3 fallback events**，gameTimeMs = [4000,6000,8000] | ✅ |
| `test_rejected_fallback_order_writes_no_event` | 桥接对 queue 返回 409 → 有 `/command/queue` 尝试、**0 条 fallback 事件** | ✅ |
| `test_one_fallback_decision_writes_exactly_one_event` | fallback 事件数 == 成功 queue 数；无重复 key；deferral ≤ fallback（状态事件允许被节流） | ✅ |

**离线 rehearsal**（`_analysis\fallback_rehearsal.py`，同一 fixture、每 tick 重复决策）：

```text
secondary queue calls = 3       fallback events = 3       deferral events = 1
fallback gameTimeMs = [4000, 6000, 8000]     per-key = {1: 3}
RESULT: PASS
```

（`1 real order → 1 event`；deferral 仍按状态事件节流，两者语义已明确分离。）
