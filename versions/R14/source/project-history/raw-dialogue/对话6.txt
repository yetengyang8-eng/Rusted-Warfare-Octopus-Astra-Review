## 2. 必须先纠正：标准实机流程不是 Battle，而是 Match

我上一轮对用户说「Start → 进入对局 → Battle，不要再跑 Match」，**这是错的**，依据如下。

### 2.1 全部历史 battle 样本都是 Match 链路的第三阶段

| 组 | economy | development | battle | 阶段间隔 |
| --- | --- | --- | --- | --- |
| #1 | 21:45:42 | 21:46:34 | 21:51:46 | 同 session、首尾相接 |
| #2 | 21:52:55 → 21:53:22 | 21:53:22 → 21:54:14 | 21:54:14 → 22:09:14 | +0.2s / +0.3s |
| #3 | 22:57:56 → 22:58:25 | 22:58:25 → 22:59:17 | 22:59:17 → 23:14:18 | +0.2s / +0.4s |
| #4（P2-A 基线） | 16:19:53 → 16:20:20 | 16:20:20 → 16:21:13 | 16:21:13 → 16:36:13 | +0.3s / +0.2s |

即：**#2 / #3 / #4 这些「基线」，以及更早的第一局，全部是 `MatchClient` 一条命令跑出来的**，其 battle 阶段开始时自带的「1 厂 + 1 矿 + 7 辆 c_tank」是它自己的 economy/development 阶段造出来的，不是地图自带、也不是用户手搓。

### 2.2 BattleClient 没有建第一座工厂的能力（代码依据）

`developer\src\io\rwagent\client\BattleClient.java`：

- 唯一的建厂路径是 P2-B 的 `planProductionFacility()`，其入口条件是 `mines >= mineTarget` **且** `lastFactoryQueueNonEmpty == true`（第 494~521 行附近）；
- `lastFactoryQueueNonEmpty` 由 `produce()` 在遍历 `/combat/production` 返回的**已建成 landFactory** 时置位；
- 因此当 `countType(landFactory) == 0` 时它**永远为 false** → 永远走 `production_facility_blocked: FACTORY_QUEUE_EMPTY` → **永远不建第一座厂**。

局 C 的崩溃报告正好是活证据：裸开局下客户端只建了 1 个矿，`production_menu` 一直是 `factories: []`，从头到尾没有任何建厂动作。**所以「Start → Battle」在裸开局下必然表现为「造矿 → 没兵可造 → 看起来卡住」**，与用户的感觉一致。

结论：**P2-B 及以后的标准实机流程 = `RW-Agent-Start.bat` → 进入对局（裸开局）→ `RW-Agent-Match.bat`（一条命令，内部 economy → development → battle），不要另开 Battle，也不要先 Battle 再 Match。** 这样才与 #1~#4 全部基线同条件。

## 3. 局 A 是干净样本：同窗口 P2-B 对比结果（情况 A 方向）

局 A 与基线 #4 方法学完全一致（同一条 Match 链路、battle 阶段同样在绝对 80 秒左右、同一初始棋盘：1 厂 + 1 矿 + 7 辆 c_tank），唯一变量就是 P2-B 代码。差别是局 A 在 **431 游戏秒原生 VICTORY** 提前结束，所以我把两局都截到 **battle 阶段 0~431 秒**的同一窗口比较（`_analysis\p2b_compare.py`）：

| 指标（battle 阶段同窗口 0~431s） | 基线 #4（P2-A） | **局 A（P2-B）** |
| --- | --- | --- |
| 生产 / 损失 | 25 / 26 | **35 / 22** |
| 生产/损失比 | 0.96 | **1.59** |
| 军队 中位 / 最大 | 4.5 / 7 | **7 / 20** |
| credits 中位 / 最大 | 1,882 / 4,324 | **792 / 2,708** |
| 工厂队列非空比例 | 93%（381/408） | 94%（385/408） |
| 已完成矿（阶段秒） | 54、119 | 65、131 |
| 第二厂 | — | planned 185s → observed 206s → completed 206s |
| `production_surplus` | — | 6 次（48、185、363、376、389、401s） |
| `INSUFFICIENT_CREDITS_FOR_FACTORY` | — | 23 次（162~185s） |
| 原生结算 | ONGOING @900s | **VICTORY @431s** |

机制侧全部按设计工作：
- `production_facility_planned: SURPLUS_WITH_BUSY_FACTORY`，`factoryCost=700`（原生实测 700）、`preferredUnit=heavyTank`、`preferredUnitCost=800`（原生实测 800）；
- 后方约束生效：`production_facility_move: RETURNING_TO_REAR` → 厂址 (1310,2470) 距建造者 113，两个厂 id 5 / 623，`production_facility_finished: FACTORY_TARGET_REACHED factories=2`，**没有再建第三座**；
- 预留逻辑生效：矿目标达成后 162~185 秒共 23 次 `INSUFFICIENT_CREDITS_FOR_FACTORY`（credits 832→1030，阈值 700+800），到 1540 才动工。

**读法**：这正是《输出5》第 5 节的**情况 A**——资金中位从 1,882 降到 792、峰值从 4,324 降到 2,708，同时生产 +40%、损失下降、军队中位 4.5→7、峰值 7→20。即「多出来的钱变成了军队」，而不是「更快地送兵」。

**但我不认为 n=1 可以结案**，理由：
1. 只有 1 局干净样本，且本局**提前以 VICTORY 结束**（#1 也曾 312s VICTORY，#2/#3/#4 都是 900s ONGOING），说明结果方差很大；
2. 第二厂完成于阶段 206s，之后只有约 225 秒双厂生产时间；
3. 90%→94% 的队列占用率说明**双厂仍然饱和**，若继续跑，可能进入《输出5》情况 C（需要更多产能/更贵科技/hard cap），这一点本局没有数据。

## 4. 新发现：建筑被摧毁会把完整战报判成 INVALID

局 C 的 `battle-1790251945113-e02bba0b.jsonl` 被 `tools\analyze_reports.py --strict` 判 **INVALID**，唯一 issue：

```
{'code': 'BATTLE_LOSS_NOT_OBSERVED', 'detail': '235'}
```

追查 unit 235：

```
economy_expansion_observed {"unitId": 235, "type": "extractorT1", "x": 1330.0, "y": 1350.0}
extractor_started / extractor_completed {"unitId": 235, "minesCompleted": 2}
own_loss {"unitId": 235, "gameTimeMs": 435512}
→ 最后一次 observation 中已不存在
```

即：**这是客户端自己新建的一座矿，后来被摧毁**，战报记录完整、诚实。

根因在 `游戏环境\P1F-冒烟环境\tools\battle_reports.py` 第 65~72 行：`new` 集合**只**由 `combat_unit_observed` 事件填充，而客户端只为「已完工、可移动、可攻击」的单位发这个事件（`BattleClient.account()` 的 `armed(u)` 条件）；建筑（矿/厂）永远不在 `new` 里，于是它的 `own_loss` 必然命中
`uid not in initial and uid not in new` → INVALID。

这不是 P2-B 引入的，但：

- P2-A/P2-B 的本意就是**持续建房**，冰岛正常 AI 下房子被拆是常态，所以**以后好局的战报很可能因为一次拆房而全部判 INVALID**；
- P2-C/D（builder 补充、矿/厂重建）会把这个缺口变成常态阻塞。

## 5. 我的判断

1. 局 A 干净、局 C 污染、尝试 B 无效——这一点证据充分，不需要裁决。
2. 标准流程应改回 **Start → 进入对局 → Match（一条命令）**；`BattleClient` 无法自立建首厂，`Start → Battle` 不是可用的评测入口。我已向用户纠正了我上一轮的错误建议。
3. P2-B 机制在实机上 100% 按设计工作；局 A 的策略结果是**情况 A 方向**，但 n=1 且提前结束，不足以定论或直接宣布进入 P3-A。
4. 建筑损失导致 INVALID 是证据链缺陷，且会在 P2-C/D 变成常态，应当先修，但修法会改动「什么算已观测」的语义，所以我不自行决定。
