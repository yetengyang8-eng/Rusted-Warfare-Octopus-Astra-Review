## 2. 我在源码里找到的真正原因（比锚点更根本）

`developer\src\io\rwagent\bootstrap\ScoutBridge.java`，`VisibleGrid` 与 `plan()`：

| 位置 | 代码 | 作用 |
| --- | --- | --- |
| `:200` | `if(distance[at]*Math.max(tw,th)>=1200)continue;` | **BFS 硬性在距锚点 1200 世界单位处停止扩展** |
| `:83` | `if(distance<120 \|\| distance>1200)continue;` | 候选前沿必须落在 120–1200 单位之间 |
| `:89` | `if(potential<12)continue;` | 候选格必须在 ±8 格（17×17）窗口内至少 **12 个未观察格** |
| `:85` | `avoid` ±3 格 | 被避开列表覆盖的候选跳过 |
| `:95-96` | `best<0` → `no_frontier` | 以上全部落空即返回 `NO_REACHABLE_UNVISITED_FRONTIER` |

### 2.1 后果

在冰岛（2900×2900）上，**规划器在任何时刻都不可能把 1200 单位以外的格子当作可达目标**。那局的情况是：军队停在家门口，锚点是离军队质心最近的 heavyTank（id 153），以它为中心 1200 单位内的未观察区域被切碎到每个 17×17 窗口都不到 12 个未知格 → **永久 `no_frontier`**，而地图上 1200 单位以外还有从未看过的区域。

### 2.2 那句 reason 名不副实

`NO_REACHABLE_UNVISITED_FRONTIER` 实际混合了四种完全不同的原因：

1. 真的没有可达的未访问格；
2. 有，但都在 1200 单位以外（BFS 根本到不了）；
3. 有，但窗口内未知格 < 12；
4. 有，但被 `avoid` 覆盖。

### 2.3 这同时说明「锚点轮换」治不了根

你《输出2》第 4 节的三层策略（anchor → 换 anchor → 全局并集）方向是对的，但**换锚点不能突破 1200 上限**：换一个更远的锚点，只是把「以它为中心的 1200 单位圆盘」挪了个位置。真正治本的是半径与阈值。

### 2.4 一个附带的技术事实

`:206` 附近的可见性/已知可通行判定是这样的：对**非可见**格，只有**以前被看见并记录为可通行**时才允许进入（配合 `:141` 的记录，注意该处 `1` 表示不可通行、`2` 表示可通行）。这是合法的迷雾约束，我没有异议，只是说明 `reachable` 天然局限于「走过的走廊 + 看过的边界」，所以它的数量会显著小于地图陆地面积——这也是我前面那个 32% 比较错在哪里的技术原因。

## 4. 环境侧的两个发现（影响以后怎么验证）

1. **交付版是在 Linux 上构建的。** 我用本机 LibericaJDK 17.0.20.1 从当前源码重建，54 个归档项里 **53 个与交付 JAR 逐字节一致**，唯一差异是 `MANIFEST.MF` 的 `Created-By`：交付版是 `17.0.20 (Ubuntu)`，重建版是 `17.0.20.1 (BellSoft)`。这既证明我的构建链可信，也说明项目的规范构建环境是 Linux（所以只有 `test.sh`，没有 `test.bat`）。
2. **`build.bat` 在含非 ASCII 字符的路径上会失败。** 它用 `for /r ... echo "%%F"` 生成 `@argfile`，cmd 用 OEM 代码页写入、javac 用另一种编码读取，导致路径里的反斜杠被吞掉（本工作区路径含中文与空格，`G:\deepseek 工作台\...`）。我改为**直接把源文件列表传给 javac，编译参数与 `build.bat` 完全一致**，并在 `developer\test-win.ps1` 里把 `test.sh` 的 13 轮 Java harness + 9 个 Python 套件搬到 Windows（`python3` → `python`）。这是工具链补齐，不涉及任何行为改动。
