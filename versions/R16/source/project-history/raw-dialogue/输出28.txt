## 先分析：这次 P0 到底查清了吗？

这一次已经不是“很可能”，而是抓到了**直接的置死调用**。

DeepSeek 的阶段二分把异常第一次出现的位置锁定在 `radius`，旧代码实际上做的是：

```java
rawInvoke(rawMethod(am.getClass(),"cj"), attacker)
```

问题在于 `am` 同时存在字段 `float cj` 和方法 `void cj()`。后者的完整效果就是把 `cu` 写成 `-1`；而 `cu` 正是游戏里的 HP 字段。

独立直接调用实验也非常干净：

```text
直接读 cj 字段        → cu=210
Field.get(cj)         → cu=210
仅取得 Method cj()    → cu=210
invoke cj()           → cu=-1
```



所以这次我们可以正式写：

> **旧 Reachability diagnostics 把碰撞半径字段 `cj` 错解析成了同名 `am.cj()` 方法，并调用了它；该方法直接执行 `cu=-1`。**

结合之前原始事故的 14/14 first representative、目标随后失去 live-unit 可解析状态，以及约 0.52 秒后被下一次 observation/own_loss 捕获，因果链已经足够强。

另一个 `ar.a()` 也确实是独立真实 bug：它是工厂调用，会创建并注册新单位。但现在可以把两件事分开：

```text
am.cj()  → 解释“枪毙/瞬死”的主根因
ar.a()   → 另一个真实世界状态污染 bug
```

DeepSeek没有把 `ar.a()` 强行当作死亡根因，这很好。

修复后的同一阶段二分里，`radius` 已经变成真正的 `Field.get`，完整默认请求之后 attacker 仍为 210/210、target 仍为 4000/4000。

所以我的技术判断是：
