## 一、Q1：`target unit not found` 查的是**全局世界注册表**，不是可见/缓存集合

端点解析目标用的是 CombatBridge 自己的 `anyUnit()`（源码，非推断）：

```java
private am anyUnit(long id){
    am[] units=am.bE.a();for(int i=0;i<am.bE.size();i++){am u=units[i];
        if(u!=null&&u.eh==id&&!u.ej&&!u.bV&&!u.cW())return u;
    }return null;
}
```

| 事实 | 证据 |
| --- | --- |
| `am.bE` 是什么 | `public static final com.corrodinggames.rts.gameFramework.utility.u bE`；`u extends AbstractList implements RandomAccess`，元素类型就是 `am` → **静态的全局世界单位集合** |
| 谁在用它 | 桥接的 `observe()` / `own()` / `production()` / `anyUnit()` **全部**遍历 `bE`；`am.bF` 只是 `HashMap` 类型实例缓存，仅用于生产菜单 |
| 过滤条件 | 仅三个存活判定：`!ej`（dead）、`!bV`（destroyed/removed）、`!cW()`（建造未完成） |
| **不是**什么 | **不是**可见性过滤。`visibleEnemies` / `rememberedEnemies` 是 `observe()` 另外构造的结构，端点从不查询它 |

**结论**：400 `target unit not found` 表示"该单位不在存活世界列表里（或已死亡/销毁/未完成）"。**因此"被探测的目标离开了世界"是硬结论**，不是可见性假象。

**独立交叉核对**（写入 `live_incident_target_reappearance.txt`）：14 个目标里前 9 个在采样后**只出现 1 次**（紧随采样的那次 observation，+3~6ms），此后 `visible-after = remembered-after = 0`；后 5 个连那一次都没有。**没有任何目标之后重新出现。**

### 普通代码错误逐项排查（不只按 B/C/D/E 抽象）

| 检查项 | 结果 |
| --- | --- |
| **集合 remove / iterator 移除** | `anyUnit()`、`own()` 均为**索引循环**且无 `remove/clear`；`observe()` 每次新建 List；`memory` 是桥接自己的 Map → **未发现共享单位列表被改写** |
| **共享列表引用** | 桥接不把内部列表交给引擎，也不把引擎列表交给任何修改者 |
| **惰性初始化 / 首次缓存** | `movementObject()` 是**首次联系才走的惰性查找**：先 `unit.h()`，失败再扫单位类型上 9 个单字母访问器 → **这是"首请求 vs 后续请求可能不同"的未解释候选机制**（本身是读操作） |
| **引擎侧写入** | 唯一被证实者仍是 `k.l.a(k.i, boolean)` → `k.i.k` |
| **更深处调用链** | **未审计**：`k.l.b/c` 内部、`y.i(am)` 的 5 个调用、`am.d(am)` 的被调用者 |

**边界（按你的要求）**：**不把 C 组的 `k.i.k` 写入认定为凶手**，它只是"唯一已知直接写状态的嫌疑点"；首请求特有机制仍开放。
