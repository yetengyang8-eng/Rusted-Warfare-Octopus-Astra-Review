### 1.2 `armyCap=24` 是 **Agent 自己的策略上限**，不是游戏限制

### 1.3 「报告比游戏退出早 71 秒停止」——**不是主循环静默死亡**，是客户端被外部终止

架构：`RW-Agent-Start.bat` 用 `-javaagent:rw-agent-bootstrap.jar` 把 API 注入**游戏进程**（`http://127.0.0.1:47653`）；`RW-Agent-Match.bat` **另起一个 java 进程**运行 `io.rwagent.client.MatchClient`。JSONL 是由这个客户端进程写出的，所以客户端一停，报告就停，但游戏进程照常运行。

`BattleClient.run()` 的主循环只有 4 条出口：原生结算（`match_terminal`）、游戏时间预算（`PARTIAL`）、2400 秒墙钟上限（异常）、以及其他异常。**这四条都会进入 `finally`，先写 `summary` 事件，再调用 `ReportFiles.finish()` 封存报告。**

而那份日志里**没有 `summary` 事件**，文件也仍是 `.jsonl.partial`。`developer\src\io\rwagent\client\ReportFiles.java` 第 4 行注释写明：`.jsonl` 表示已关闭并 flush 的报告，被中断的运行保留 `.jsonl.partial`；只有 `finish()` 会写入新路径并原子改名。

**结论**：`MatchClient` 进程是被外部强制终止的（关闭控制台窗口 / Ctrl+C / 被结束进程）。游戏作为独立进程又活了 71 秒，直到从菜单点「退出游戏」。因此**那局的 INVALID 是机制按设计工作，不是缺陷**，也不存在「Agent 主循环悄悄死掉」需要排查。你建议的 `agent_tick_alive` 低频心跳我仍然赞成——它能区分「策略决定等待 / 规划器没目标 / 进程已死」三种状态，很便宜。

## 3. 你关心的 A/B 判定：**是 A（规划器/搜索 bug），不是 B（能力边界）**

我用地图数据做了连通性分析，并对判读方法做了两次标定。

### 3.1 方法与标定

- 地图 `[p2]Ice Island (2p).tmx` 是 Tiled 格式，共 4 层：`Ground`、`Items`、`Units`、`set`（`set` 层是地形规则层）。
- 地形按 tileset 命名区分：`Ice`、`Snow` 为陆地；`Shallow Water`、`Deep Water`、`Ice ShallowWater - Ridge` 为水。
- **标定①（取向）**：用「末帧所有己方单位都必须站在可通行格上」检验——不翻转行序时 **28/28 单位（25/25 机动单位）都在陆地上**；翻转行序只有 21/28。故行序不翻转。
- **标定②（哪一层是规则层）**：用「己方基地必须与建造者自己走过去建成的矿连通」检验——
  - 只看 `Ground` 层：基地在 7510 格的连通块，己方矿在 304 格的另一个块，**不连通（伪）**；
  - 用 `set` 层：两者**连通（真）**。
  - 因此 `set` 层才是能复现真实通行性的那一层。

### 3.2 结果

用 `set` 层 + 8 连通：

- 可通行格 **10120**，**只有 2 个连通分量，最大分量 10112 格（99.9%）**。
- 以下 5 个位置**全部落在同一个分量（0 号，10112 格）**：

| 位置 | 世界坐标 | 地形 | 分量 |
| --- | --- | --- | --- |
| 己方指挥中心 | (1270, 2390) | Ice | 0 |
| 己方矿 | (1110, 2190) | Snow | 0 |
| 己方建造者 | (1187.9, 2220.2) | Snow | 0 |
| **敌人最后目击点** | **(653.7, 1595.1)** | **Ice** | **0** |
| 首个敌人矿 | (1590, 670) | Snow | 0 |

**结论**：敌人最后被看到的位置，与己方基地属于**同一块连通陆地**。所以「剩余未探索区域属于陆军不可达连通分量、需要用海军」这个 B 假设，**对这个最后目击点是站不住的**。这一局属于你定义的 A 类：同一陆军连通区域，却在只探索约一半时报「无前沿」。

### 3.3 数量对比（支持你的 Priority 6）

- 整块连通陆地：**10112 格**
- 同局 `army_frontier_plan` 末条事件里锚点单元的 `reachableTiles`：**3255 格（约 32%）**
- 同局 `scout_visibility` 的 `exploredTiles`：**10717 格**，且从约 395 游戏秒起冻结不再增长

也就是说：地图很大程度上**已经看过了**（10717 已远超连通陆地 10112），但**规划器给自己划的可达范围只有 3255 格**，锚点 `builderId: 153` 是一辆当时停在基地附近的 heavyTank。这与你的 Priority 6（取全部机动单位可达区域求并集）以及我对「锚点绑死」的判断一致。

### 3.4 我保留的边界（请不要把它当成已封死的结论）

- 我是从地图文件反推通行性，**不是游戏的 native pathfinding**。连通 ≠ 一定可寻路（建筑占位、隘口、单位移动类型都可能再挡一层）。
- 但它足以**排除「跨水不可达」这个解释**：因为「我的判读把两个点放进同一个连通块」这件事，只可能因为我的判读过于宽松，而不可能因为过于严格；而 `set` 层判读已经通过了两次标定。
- 另外：`Ground` 层判读会把己方基地和己方矿错分成两座岛，这本身也说明**离线 tmx 分析不能替代你在 1.1 之外建议的那个运行时检查**（由原生可达性回答「敌我是否同一连通分量」并输出 `reachableMapRatio = landReachableTiles / totalLandTiles`）。我建议这个字段照做，作为以后判断 A/B 的标准证据。
