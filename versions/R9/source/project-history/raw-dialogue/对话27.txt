## 2. 本轮最重要的发现：诊断在活体游戏里**创建单位**（代码缺陷，已修复）

`sandbox_bisect.txt` 第一次运行时暴露了一个异常现象：**注册表在每个 arm 后 +1**（4→5→6→7）。定位到 `movementObject()` 的字段扫描里包含 `a`。实测（`type_accessor_factory_probe.txt`）：

```text
单位类型 ar 的 9 个单字母访问器，逐个调用并观察 am.bE：
  u=+0  k=+0  n=+0  m=+0  e=+0(ERR)  d=+0  c=+0(ERR)  b=+0(ERR)
  a=+1   ← 返回 com.corrodinggames.rts.game.units.e.n（新单位实例），并注册进全局注册表
```

`movement_resolution_probe.txt` 复现事故顺序（`r()` → `u,k,n,m,e,d,c,b,a`）：**只有 `a` 这一步 registryDelta=+1**。

而事故候选 `0beaf504` 的 `movementObject()` **正是以 `a` 结尾的扫描**：

```java
Object type = r(unit);
for (String name : {"u","k","n","m","e","d","c","b","a"}) { ... }   // a() = 工厂
```

**结论**：在那一版里，**每一次 reachability 采样都在真实对局中创建并注册一个新单位**。这与"每批第一次请求"的时间结构完全一致（每次采样都会走这条惰性查找）。这解释了我在《对话26》§Q2 标记的"首请求特有、未解释的惰性查找"——**它不是无害的读操作**。

**已修复**：扫描列表改为 `{u,k,n,m,e,d,c,b}`，**永不调用工厂访问器**；全部不匹配则 movement class 留空并在 payload 说明（`MOVEMENT_ACCESSOR_NAMES` 常量 + `reportSecondaryFallback` 之外的注释）。事故顺序仅在 `incident=1`（沙盒、需 arm）下保留。

**边界（不越界宣称）**：这证明了"诊断会创建单位"，**尚未证明**它就是 attacker/target 失去 live-world 状态的原因。但它是**目前唯一被证实的、发生在每次采样中的真实状态突变**，且与 first-request 结构吻合。
