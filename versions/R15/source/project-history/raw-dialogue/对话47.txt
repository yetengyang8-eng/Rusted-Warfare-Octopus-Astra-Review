**③ 谱系**：安装件 == dist == 当前源码内容（whole `efd51831…`、contentDigest `6fec7a0c…`、58 条目）；
`aVsInstalled=[]`、`aVsDist=[]`；冻结件 `0681b4f7…`、game-lib `8a550a37…` 未变。
whole-file SHA 只作本次构建身份，候选身份仍以 **contentDigest** 为准。

**④ 聚合器拒绝能力（我构造的变异样本，不看它的用例）**：
- **硬拒绝（exit 2、不产出结果）**：一批候选 contentDigest 被改 / 一批地图被改 / episode.json 与 batch.json 登记不一致；
- **在结果内标记并排除（exit 0，但 `reportStatus=INVALID` + 具名 `reportIssue`）**：
  报告被翻坏一个字节 → `battle raw SHA mismatch`；报告被追加外来 session（且两处登记 SHA 都同步更新，
  让 SHA 检查通过）→ `battle session mismatch`；两种情况该局都**不进指标**（`valid=1 / n=1`），另一臂不受影响。

- **没有静默混算**：两档都不让被污染的数据进入数值。

**⑤ 我自己的最小 campaign**：AB + BA 两批、`--battle-seconds 240`。四局全部 `PARTIAL/ONGOING`，
运行器按 match 模式定义记 `FAIL`、批次 exit 1 —— 这**不是编排失败**。
聚合结果：报告 `VALID`、`partial=2`/臂、`nativeCompleted=0`、**指标 `n=0`/均值 `null`**、分母仍 `attempted=2`；

## 3. 我的两条独立发现（请记入下一轮）

1. **迁址陷阱（Codex 未写明）**：把 run 目录复制/搬走后若不重算并回写报告 SHA，
   聚合器会把**每一局**判成 `battle raw SHA mismatch`，结果看起来像"没有数据"（**exit 0、n=0**，不报错）。
   影响归档/campaign 流程。对策：归档保持字节与路径原样（Codex 的 ZIP 做法正确），搬动后重算 SHA；
   **验收必须看 `validBattleReports` / `invalidOrMissingReports` / `n`，不能只看退出码**。
   （我自己前两次"控制组失败"就是这个坑，属我的夹具缺陷，不是聚合器问题。）
2. **磁盘成本**：每个 run 目录约 **76 MB**——`stage()` 对 `assets/libs/res` 用了 copytree 回退
   （Windows 建目录符号链接需要权限）。四批 ≈ 300 MB；N 批 campaign 线性增长。
   建议下一轮把 `stage()` 改成 **junction**（`mklink /J`，无需管理员权限），并给 campaign 加磁盘预算检查。

## 4. 下一阶段评估（只读结论，不施工）

### 4.1 主任务：建议就做「A/B campaign v0」（受控并行）

理由：v0 的三块拼图已经齐了——`run_headless --profiles/--profile-order`（每实例 profile）、
`live-claims.json` + `--reap`（崩溃恢复）、`aggregate_ab.py`（跨批聚合与拒绝）。
campaign 只差编排层，不需要碰策略或引擎。**必须包含的最小内容**：

1. **crossover 驱动**：给定 N，自动交替 AB/BA，逐批落 `campaign.json`（批次目录、顺序、开始/结束、退出码、聚合摘要）。
2. **断点续跑**：campaign 清单 + 每批完成标记；重跑只补缺口（幂等），不重跑已完成批次。
3. **失败策略（关键，本轮实测教训）**：**必须区分"编排失败"与"比赛没有原生结果"**——
   我的 240 秒 campaign 四局全 PARTIAL，运行器 exit 1，但那是**正常数据**。
   规则建议：批次 exit≠0 且 `parallelProof=PASS` 且报告 VALID ⇒ 记为 `NO_NATIVE_RESULT` 继续；
   只有 proof/session/SHA/身份异常才中止该批并（可选）重试。
4. **聚合收口**：全部批次一次聚合；报告里同时给 `attempted / validBattleReports / partial / invalidOrMissingReports / n`
   与逐批路径；**不产出"哪个 profile 更好"的结论**（延续 v0 的克制）。
5. **磁盘与清理**：junction 化 + 每批体积记录 + 保留/清理策略（证据目录不可原地搬家）。
6. 样本量口径由裁决决定：**我建议先只做"给定 N"的基础设施，不在本轮定 N**。

### 4.2 只读侦察 1：同局双 Agent / self-play 最小接口与风险图

**结论：不适合作为下一轮主任务。** 依据（我已核过代码）：
`HeadlessRunner` 明确 `Only local matches are supported`（`engine.bX.B || engine.cb.j()` 即拒绝），
其 CLI 只有 `--map/--port/--speed/--max-wall-seconds/--frames/--difficulty`；
`RuntimeBridge.start(engine, port, true)` 是**每引擎进程一个桥、一个端口**，且没有队/玩家参数。
要在同一局里跑两个 Agent，至少需要：① 一局两个非 AI 玩家；② 两个桥分别绑定不同队；
③ 命令按队路由。这三项都指向**引擎/桥接层**（与 P0/Lab 边界相邻）。
建议：只做**只读侦察**（能否在不写引擎状态的前提下把桥绑到第二个队），产出一页风险图，**不进入实现**。

### 4.3 只读侦察 2：seed 是否存在"安全初始化期注入口"

**结论：目前没有找到，且按裁决规则应判"不适合主线"。** 已知事实：
`HeadlessRunner` 没有 `--seed`；运行时只**读出** `engine.bJ` 并写进 `runtime.json`，同时自报
`seedReproducibilityVerified=false`；匹配创建调用路径（`engine.a(true, com.corrodinggames.rts.gameFramework.s.b)`）
没有暴露 seed 参数。**在匹配运行中写引擎内部状态属于 Lab 禁区**。
建议：只做一次有界的只读探查（是否存在**匹配前**的配置/偏好/大厅级 seed 入口）；
若不存在，就承认"A/B 是同条件不同随机"，用 N 与配对设计承担方差，**不把 seed 注入列为主线任务**。
