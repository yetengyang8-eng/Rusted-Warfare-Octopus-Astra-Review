## 2. `produce()` 的代码级事实（对应《输出7》§2 的 8 个问题）

`developer\src\io\rwagent\client\BattleClient.java`：

| # | 问题 | 事实（行号） |
| --- | --- | --- |
| 1 | 工厂遍历顺序 | 按 `/combat/production` 返回的 `factories` 数组顺序（第174行），该顺序 = 引擎单位表顺序（≈创建顺序）。实测老厂恒在前：第4局 662 次 `(5,642)`、局A 219 次 `(5,623)`，**从未反序** |
| 2 | 谁先得到生产机会 | 老厂（id 5，已 T2）排在前面，但约 95% 的 tick 里 `queue != 0` 被跳过（第176行）→ **那一 tick 的机会落到新建 T1 厂** |
| 3 | 一次能下几张单 | **每 tick 最多 1 张**：成功下单即 `return true`（第204行），两厂不是并行生产，而是共享 1 条/tick 的配额 |
| 4 | c_tank / heavyTank 评分 | `tank`/`c_tank` = 1、`heavyTank` = 3、`upgrade` = 5；`affordable` 是硬过滤（第187行） |
| 5 | 买不起 heavyTank 是否立刻退化买 c_tank | **是**：只看「买得起」的项打分，没有任何为高价值单位预留资金的逻辑（第188行） |
| 6 | T1 买 c_tank 会不会挤掉 T2 的重坦预算 | **会**：两厂共用 `player.credits`，无全局预算；T1 花掉 350 后，T2 下次空出时的余额常常 < 800 |
| 7 | `BANKING_FOR_UPGRADE` 的对象 | **该厂自己的升级**：仅当 `army>=10` 且该厂菜单里仍有 upgrade 时跳过该厂（第197~200行），逐厂判断、非全局 |
| 8 | 局部最优还是全局目标 | **纯每厂局部最优**；没有全局生产预算，也没有 `heavyTank` 或任何兵种的全局目标 |

补充一条《输出7》§3 关心的事实：**第二座厂从未升级**。三个双厂样本里新厂的 tier 集合都是 `[1]`（局A 的 623、第3局的 548、第4局的 642），而老厂是 `[1, 2]`。局A 里新厂曾下单一次 upgrade 但比赛已结束；第4局 900 秒里新厂始终没升（资金被 350 元单位持续抽干，upgrade 一直买不起）。

**结论**：现在没有任何机制保证「高价值工厂优先获得有限资金」。这正是《输出7》§6 设想的 `Global production budget` 所针对的问题，且**不需要新增日志就能证明它已经发生**（见下节）；只有「某厂想买但买不起」的逐 tick 记录目前缺失，可用 §4 建议的 `production_blocked` 补上。

## 6. 下一步（P2-C1）遇到一个《输出7》没有覆盖的技术前提，需要裁决

《输出7》把 P2-C1（`builderTarget = 1` 的恢复闭环）排在下一步。我查了桥接现状，**目前不存在任何「生产建造者」的能力**：

| 位置 | 现状 |
| --- | --- |
| `CombatBridge` 第77行 | `/command/queue` 明确要求 `"landFactory".equals(factory.r().i())`，对指挥中心直接 409 |
| `CombatBridge` 第78行 | 队列判定用 `EconomyBridge.queueCount()`，它只对 `FACTORY` 类有效（第295~299行），指挥中心不适用 |
| `CombatBridge` 第98行 | `/combat/production` 只列 landFactory 单位，指挥中心的动作列表根本读不到 |
| `EconomyBridge` | 只有 `/command/build-extractor`、`/command/build-factory`（都是「建造者去盖房」），没有「生产单位」 |

所以 P2-C1 至少需要新增：①只读地列出指挥中心（或其它生产建筑）的动作；②一条下达「生产建造者」的命令；③该建筑队列/在产状态的判定。这是**新的桥接 API**，不是纯客户端改动。我不擅自扩大范围，请裁决。

**Q1**：P2-C1 是否可以新增上述桥接能力？如果可以，你倾向哪种形态：
(a) 新增专用端点（如 `/economy/builders` 只读 + `/command/produce-builder`）；
(b) 把 `/combat/production` 扩展出一个通用的 `producers` 数组（列出所有可产单位的自有建筑及其动作），并让 `/command/queue` 接受任意这类建筑。我倾向 (b)：一次把「生产」抽象清楚，避免以后为 airFactory/实验工厂再开一次口子，但它的改动面比 (a) 大，且触及既有端点。

**Q2**：《输出7》§4 的 `production_blocked`（逐 tick 记录「某厂想买什么、买不起什么」）要不要现在就加？它是纯诊断，能把「T1 抽干资金 → T2 退化」的因果链从推断变成逐帧证据。我倾向加，放在 P2-B2 行为修改之前的同一候选版里。

**Q3**：`heavyTank` 是否对空，用哪种只读探针确认？我倾向在 `developer\tests\` 里加一个 `CapabilityHarness`（反射原生单位元数据，打印若干兵种的 `canAttackFlyingUnits`），并纳入回归；它不改客户端与桥接行为。

**Q4**：在 P2-B2 生产调度与 P3-A 之间，你希望我用哪一份证据来定序？我的建议是：**先看 Q2 的 `production_blocked` 采到的资金争抢链**——如果证实 T2 老厂经常因为 T1 刚花了 350 而买不起 800，那 P2-B2（T2 预算优先）应优先于 P3-A；第4局 342/455 的菜单比例已经强烈暗示这一点，但还缺逐帧因果。
