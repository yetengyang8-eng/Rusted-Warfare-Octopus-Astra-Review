## 5. P2：只修一个已有证据支持的能力响应断点

**选题规则**：优先选择“存在合法可行窗口，却持续不能把需求推进到下一步”的可修缺陷。若 A 局只是处于真实资金/军力/生存约束，不能为了制造投资次数而绕过保护；此时应选择证据支持的早期战损或任务完成问题，并写清对原计划的调整。

候选改动由根因决定，例如任务占用造成的投资长期等待、资金承诺与生产菜单脱节、失败次数/释放转换错误。只实现其中一项，并记录会新增什么行为、何时保持原样、何时明确拒绝；不预先规定放宽哪个阈值。

**验证顺序**：

1. 建立能让旧代码暴露该机制的最小 E2，用相同输入证明新代码闭合对应转换；覆盖资金不足、基地急迫、未知目标/地形、无合法菜单、失败后释放与重试上限等相邻边界。
2. 验证共享命令间隔、己方与玩家身份、单单位单任务、已付费队列计数、baseline builder 保留，以及 Target Guard/UNKNOWN 原语义。对预算终点的活动任务单列，不要求所有未完任务伪装为已完成。
3. 在获准的隔离原生环境先做短局命令与报告检查，再做相同已记录地图/位置/设置/时长的自然长局。最终 JAR 与中间构建证据分开。
4. 用基线与单项候选交替运行 AB/BA。低成本工程筛查至少每臂 3 个 Spain 长局，并补每臂 1 个 Big Island 对照；这不是胜率统计充分样本。预先固定设置及预算，报告全部失败、预算到期、分布与异常值。无法证明 seed 重现时称为同配置重复样本，不称同 seed 的配对因果实验。
5. 长局若使用现有 A/B campaign，须先修正/验证其当前 1800 秒上限及向 runner 传递的 budget、poll 设置；不能只改数值绕过校验。此基础设施修改单独验收；也可先使用已有单实例 runner 的显式记录逐局比较。

**交付**：一个主题清楚的修复候选、旧/新 E2 对照、完整回归、最终候选的原生与用户桌面复核材料，以及带运行上下文的基线/候选对照。

**通过标准**：目标机制在确定性测试中消失；不存在新契约违规；自然样本出现预期的执行链或如实记录未触发；候选不系统性损害 builder 存活、主力可用性和报告完整性。以“合法可行窗口内需求等待时间、成品观察与任务完成率、响应者存活、角色化损失与资金约束”为主要工程指标，不以最高 armed、投资次数或花钱总量单独判优。数值门槛在执行对照前依据 P0 分布登记，结果出来后不得改门槛。

**非目标**：不同时改 cap、兵种评分、侦察威胁缓冲和经济分配；不把 queued 当作执行，不把团队伤害归为响应者独占击杀，不要求限时样本必然胜利。

## 6. P3：补齐无 builder 的原生起步

**输入**：Spain 原始出生位“有基地、无 builder”的合法己方状态，以及 `MatchClient`、`EconomyBridge` preflight 和现有 Builder 恢复路径。

当前 `MatchClient` 仅接收 `RUN_ECONOMY_OR_OPENING` / `RUN_DEVELOP` 等已具备工作起点的预检结果；Battle 内的 builderRecovery 不等于 Match 前能够自举。应单独定义开局 bootstrap 阶段，而不是把操作员前置生产隐去。

**施工**：先从真实己方基地菜单验证可用的 builder 动作、资金和队列；必要时添加最小白名单桥接。无 builder 且没有待产 builder 时发出一次正常生产命令，记录回执、队列和新己方单位观察；确认成品后重做 preflight，再进入既有 Economy/Development/Battle。已有 builder、已有 builder 队列、资金暂不足、无可用生产者、菜单不支持与超时分别处理，避免重复生产和无限等待。

**交付**：受预算约束的启动阶段、命令与成品证据、无 builder/已有 builder/失败路径 E2、隔离原生起步样本，以及更新后的启动上下文标记。

**通过标准**：Spain 原生无 builder 条件下无需人为先造单位即可进入原有 Match；同一启动过程没有重复排队；正常已有 builder 开局不新增命令；失败有明确理由和可保留报告。用户桌面样本需明确从原始出生状态开始才能补上对应桌面能力证明。

**非目标**：不新增多玩家控制，不修改原地图或资源，不顺带调整前期经济/兵种。P3 样本与历史两场 operator-bootstrapped Spain 局分开，也不与其他起步条件不同的历史样本混合，不混入 P2 的相同起点对照。

## 7. P4：根据结果串行处理响应者生存与经济溢出

P2/P3 稳定后，依据新证据先选择下列一条；完成一条的独立验收再开启另一条。

### P4a 响应者生存与成组完成任务

**输入**：有任务但无法完成的自然样本，按出生、认领、出发、遇敌、损伤、撤回/死亡分类；区分缺少接近位置、战斗实力不足、任务被抢占和采样缺失。

**交付**：围绕已证实原因的最小任务改进。若确需成组响应，先明确所需兵种能力、集合/出发条件、等待上限、角色 ownership、伤亡与撤回转换，再实现；不得把所有响应者无条件堆成大队。重伤返回也不等于修理策略已完成。

**通过标准**：旧失败机制可复现并被改进；任一单位同时只有一个 owner，接管和释放有证据；目标仍须合法兼容和有已知接近证据。工程对照观察任务成本、存活到达、可见伤害、合法解决与主力损失，不以移动距离或单次伤害替代完成。

**非目标**：完整海军、运输、潜水形态控制、修理/回收体系、通用多编队框架、全图必胜保证。

### P4b 经济溢出与投资价值

**输入**：按窗口归因的余额/收入/消费、已付费队列、施工与升级、产能闲置、主力短缺、未满足任务。Spain A 的低军力高消耗与 B 的高军力/高盈余分开分析。

**交付**：选择一个真实投资失配机制修复，例如无军事消费出口时仍继续增加收入，或存在有效能力需求却被重复矿投资挤占；保留可解释的预算/拒绝理由。明确估计收益与原生实测成本的来源。

**通过标准**：相同输入夹具中不再发生目标投资失配；资金储备、恢复能力和任务进展不劣化。对照同时评价盈余、有效军力恢复、需求完成和损失，不能靠取消必要建设或无价值支出来“改善余额”。

**非目标**：降低余额本身、自动全参数调优、全经济系统重写、单纯继续提高 hard cap。

## 8. P5：基线晋级与交付合同

**输入**：本轮一个独立主题的最终代码、不可变交付件、完整回归、预先登记的验收指标和原生/桌面报告。

**交付**：新基线记录与回退入口，包括 parent baseline ID、源码 commit、构建/JDK、JAR whole SHA、contentDigest、game/知识资源身份、最终候选对应的全部证据、已知限制及未触发分支。下一版拟使用 `RW-BASELINE-2026-09-30-GS-v2`；若到其他日期完成，另立日期和版本，不改写 v1 历史。

**晋级必须同时满足**：

1. 源码、构建资源、最终 JAR、实际安装候选具有可复查谱系；保存 v1 回退件。中间候选不并入最终候选验收。
2. Windows 完整回归零失败，必要平台用例真实执行；相关 Linux/原生 E2 另列。遇到平台限制则明确未完成，不能晋级为“验证已补齐”。
3. 最终候选完成预期的隔离原生行为复核，用户桌面复核对应其真实运行条件。若目标自然分支未触发，保留候选身份并标未验证，不用模拟结果替代桌面结论。
4. 所有采纳结论有 raw SHA、运行上下文、审核结果和失败样本。ownership、合法视野、命令预算、资金与报告完整性没有新违规。
5. 针对该单项改进的预登记通过标准成立。有限样本的工程改进只按有限样本陈述；胜率/因果优越性需要另行设计充分重复实验，不能随工程基线自动宣告。
6. 最新状态入口、README 当前身份、基线清单、安装/回退说明一致。桌面已运行与 Windows 测试矩阵通过分别记录。

**非目标**：发布即表示所有地图均可靠、证明完整零人工起步（除非 P3 验收已完成）、完成 same-game 双玩家或自对弈。
