**核心主张**

不要再往"造工程师"上叠规则，而是把工程师从普通单位池里彻底独立出来，当作**特种单位**来设计一条完整的生命周期，并让它形成可重复的闭环。

**要治的病根**

第二局的死循环是：潜艇需求未解决 → 系统认为仍缺能力 → 继续造 combatEngineer → 新工程师被 PROSPECT 或建设逻辑征用 → 阵亡 → 需求仍未解决 → 再造，最后 14 个工程师流水线送死。拆开看有三个缺口：需求没有"所有者"，工程师没被隔离保护，"完成"没有真实验证（所以 capability need 一直卡在 0 resolved）。

**七层思路**

1. **需求 → 任务**：每个能力需求先落成明确任务（taskId、类型、目标点、所需能力、风险、优先级、已分配工程师、状态）。工程师服务任务，而不是服务"工程师数量不足"。
2. **一任务一工程师**：一旦进入 ENGINEER_ASSIGNED，就不再因"需求未解决"触发补产。只有确认死亡、无法到达、能力不足、被高优先级任务正式抢占、任务规模需要多人这几种情况才能补。
3. **独立状态机 + 优先级隔离**：从 IDLE_SPECIALIST 经 TRANSIT、APPROACH、EXECUTING、VERIFYING 再回待命，另有 BLOCKED、NO_PROGRESS、THREATENED→RETREAT、DEAD 等失败分支。标记为 SPECIALIST 后，PROSPECT、普通扩矿、普通施工都不能再征用它。
4. **出发前先做路线风险判断**：复用已有的敌军分组和危机信号。低风险单独去，中风险等护卫，高风险暂缓。3500 的 combatEngineer 是高价值资产，不能让它一路走进危险区。
5. **工程师与护卫队主从绑定**：任务同时绑定工程师和护卫队。护卫先接敌，工程师留在后方，我方威慑占优才继续推进，被反超就按已定义的撤退机制退向友军。工程师因此成为"危机—分兵—撤退"模型的第一个实际使用者。
6. **验证真实效果**：不以"到附近了"为成功，而是按任务类型走验证链，通过后才算 RESOLVED。反潜是目标入视野 → 具备攻击能力 → 发生攻击 → 目标受伤 → 死亡或位置清空；施工是下令 → 建筑出现 → 进度上升 → 完成；维修是靠近 → 维修动作 → HP 上升 → 达到阈值。
7. **完成后回特种待命池，不回经济系统**：在安全区待命、跟随主力后方、修理附近单位或做低风险工作，但不因为"闲着"被派去边缘探矿。

**压成一条闭环**

能力需求 → 建任务 → 找闲置工程师（没有则预留资金生产）→ 绑定任务 → 路线风险判断 → 必要时配护卫 → 前往执行 → 验证真实效果 → 任务解决 → 回到待命池。

失败则先分类原因，再撤退、重规划、等护卫或换人，只有确认工程师失效后才允许补产。

**底层逻辑**

整体是四个替换：用任务所有权替换"缺就补"的数量逻辑，用隔离替换与经济逻辑共享单位，用事前风险判断替换事后补救，用结果验证替换"到了就算完成"。

文档建议把它作为 Astra 的独立阶段（Engineer Operations / Specialist Lifecycle）来做。它比继续修单个 `NO_OBSERVED_PROGRESS` 更重要，因为它一次打通生产、任务归属、移动、生存、执行、验证和回收利用。目标不是"让工程师能移动"，而是让一名工程师被需求催生出来，完成一个真实任务，再活着进入下一次待命。
