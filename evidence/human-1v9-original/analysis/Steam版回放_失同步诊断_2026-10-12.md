# Steam 安装与 10p 西班牙混战回放：失同步复查

日期：2026-10-12

## 结论

**Steam 路径确实揭示了此前忽略的运行链，但直接使用 Steam 游戏库仍未解除我们无头解析程序在约77.4游戏分钟遭遇的失同步。**

用户亲自在原游戏客户端观看，未发现异常。因此目前不能证明“回放文件损坏”；更准确的表述是：**独立无头回放/采样驱动与真实游戏客户端运行链存在尚未解决的确定性差异**。

## 2. 独立对照实验

所有工作写在 `G:\deepseek 工作台\_analysis\human_1v9_20261012\` 下，使用复制的回放、地图、`preferences.ini`、`mods`、`game-lib.jar`。本次未修改 Steam 安装文件或原始回放。

### 测试 A：Steam 原版库 + Steam 配置副本

目录 `stage_steam`，日志 `steam_330k/replay.log`。

能完整加载地图、队伍、开始逐帧重放。**约77.4分钟再次失同步，第一条对象类型错误：**

`desync:object id:272292 was found, but with type game.f instead of game.units.y`

随后有各种单位控制 ID 不符。这个错误与前一次旧分析环境中的第一条错误 ID 完全一致。

### 测试 B：Steam generated_lib 生成库 + RWPP 依赖

目录 `stage_generated`，日志 `steam_330k/generated8.log`。

- 生成库需要 Kotlin/Java17、RWPP Koin 初始化与全部 `app/*.jar`，还引用 `rw.camerafollow.MatchTelemetry` 观战工具。
- 已在**隔离采样代码**里建立 RWPP Koin 最小引导，加入 CameraFollow jar，并拷贝原始 replay 到 stage 的 `replays/` 供观战元数据读取。
- 生成库的渲染注入会要求 LWJGL OpenGL context；无头分析模式缺少此上下文，因此仅为实验提供了一个**旁路渲染的 GameInject stub**（只位于分析 classes，原始 Steam/RWPP jar 不变）。这并不等同于完整 GUI 运行链，所以本实验的“失同步”不能证明用户真实客户端有问题。
- 在前期，Ares 的 5、10、15、20、25分钟重坦、工厂、收入和现金快照与前一实验和旧解析**完全一致**。
- 但在约77.4分钟也再次出现**相同的首个 ID 类型错误 `272292 game.f instead of game.units.y`**。
- 330,000 tick 试验结束时，两个无头样本都继续处于 replay=true；并未验证完整终局。

**解释**：文件来源/版本/地图差异并非根因；直接换 Steam/RWPP 库不足以使当前无头采样器越过该问题。应该优先查采样器模拟循环与真实 GUI 播放器的状态推进、对战命令/对象生成顺序差异；也不能排除生成库在原始 GUI 中具有未被无头实验保留的作用。

## 3. 后续最值得投入的路径

1. **原始命令流的无模拟提取**：已成功得到105,267条原生回放命令、Ares18,385条。扩展二进制解码以导出真实命令时间、actor ids、目标单位 id、坐标及生产动作，能避开模拟失同步，用整局184分钟分析分兵、点杀、生产与改向。
2. 若确实需要77.4分钟后的真实单位状态、HP/击杀/收官，则应让采集钩子跟随真实 Steam/RWPP **GUI 重放执行路径**，或实现与其严格一致的图形/主循环、replay frame 调度；不要继续把 `engine.b(1f,16)` 的人工驱动当成确定性真源。
3. 以原生 replay checksum 与 object-id 272292 的首个失配时间为定点回归条件，修完必须确认能穿越77.4分并且原版结局与用户目测一致，再恢复后半局证据可信度。
